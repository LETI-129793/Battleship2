## 1. Cheiro no código escolhido

O cheiro no código escolhido foi **Large Class**, do catálogo de Martin Fowler.
Este cheiro ocorre quando uma classe acumula demasiadas responsabilidades, métodos ou variáveis de instância, tornando-se excessivamente complexa, difícil de manter e violando o Princípio da Responsabilidade Única (SRP).

---

## 2. Mapeamento entre o cheiro e a inspeção

| Elemento | Descrição |
| :--- | :--- |
| **Cheiro no código** | Large Class |
| **Inspeção no IDE** | Class with too many methods / Method count |
| **ID da inspeção** | `MethodCount` |
| **Métrica utilizada** | NOM (Number of Methods) / Contagem de métodos da classe |
| **Valor-limite configurado** | 15 |
| **Limitações** | A inspeção utiliza um limite absoluto e não permite reproduzir diretamente uma estratégia polimétrica combinada com condições lógicas complexas e valores relativos ao sistema. O limite de 20 foi escolhido para balizar a volumetria de operações da classe, mas métricas isoladas de contagem não contemplam a coesão interna (como TCC) nem o acoplamento externo (como ATFD). |

---

## 3. Configuração e resultados

Foi criado um perfil personalizado do Qodana para executar a inspeção `MethodCount`, com o limite `m_limit: 15`.
A análise inicial identificou instâncias de classes que ultrapassavam este limiar de volumetria de métodos no projeto BattleShip2.

## 4. Teste do Quality Gate

Foi criado o ramo de teste e aberto o respetivo Pull Request. Em que após um estado onde se colocou uma class com mais de 15 métodos, para falhar o quality gate.
De seguida alterou-se essa class e o quality gate já funcionou.

* **Execução com sucesso:**  
  https://github.com/LETI-129793/Battleship2/pull/15#issue-6270581014
  *Após a refatoração e remoção dos métodos em excesso, o Qodana não identificou infrações e o Quality Gate passou.*

  ## 5. Proteção do ramo principal

A proteção do ramo `main` foi analisada, mas não foi configurada. A operação depende de permissões administrativas num repositório partilhado, e a seleção do check obrigatório exigia distinguir vários jobs com o mesmo identificador qodana.
O Quality Gate foi validado nos dois estados, mas não foi demonstrado o bloqueio do merge através de uma regra de proteção.

---

## 6. Reflexão

O Qodana identificou de forma eficaz classes com um número elevado de métodos, detetando corretamente a classe grande introduzida no teste. A inspeção pode produzir falsos positivos, uma vez que uma classe com muitos métodos pode estar estruturada de forma coesa (por exemplo, um helper ou facade puramente modular), bem como falsos negativos, caso uma classe seja pequena em número de métodos mas possua acoplamento e lógica interna excessivamente densos. 
O número de problemas detetados depende diretamente do valor-limite configurado, sendo que limiares mais restritos geram mais alertas.
Comparativamente às estratégias do livro *Object-Oriented Metrics in Practice*, a configuração utilizada é uma aproximação linear, pois carece da capacidade de cruzar métricas de tamanho com métricas de coesão (TCC) e acoplamento (ATFD) de forma relacional.
